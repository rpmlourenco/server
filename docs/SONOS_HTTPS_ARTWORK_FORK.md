# Sonos HTTPS artwork fork

This document describes the personal change maintained on the
`sonos-https-artwork` branch, how the Home Assistant image is built, and how to
update the fork when a new stable Music Assistant version is released.

## Purpose

The Sonos provider can send an artwork URL to a player. In some installations,
Sonos needs an HTTPS URL that is reachable through the external Home Assistant
address instead of the local HTTP URL normally generated by Music Assistant.

The patch adds the advanced **Artwork HTTPS base URL** option to the Sonos
provider. When configured, the provider keeps the image identifier generated by
Music Assistant but replaces the URL origin with the configured HTTPS proxy.

Example configuration:

```text
https://YOUR-HOME-ASSISTANT-ID.ui.nabu.casa/ma-sonos-artwork
```

The `/ma-sonos-artwork` endpoint is provided by the Home Assistant integration
maintained in
[`rpmlourenco/ma-sonos-artwork`](https://github.com/rpmlourenco/ma-sonos-artwork).

## How the final image is built

`Dockerfile.personal` starts from an explicit stable version of the official
image:

```dockerfile
ARG UPSTREAM_VERSION=2.10.1
FROM ghcr.io/music-assistant/server:${UPSTREAM_VERSION}
```

It then copies only the five modified Sonos provider and translation files into
the existing Python installation. The final image therefore retains all
components and dependencies from the official distribution and replaces only
the implementation required for Sonos HTTPS artwork.

The workflow publishes an ARM64 image under this name:

```text
ghcr.io/rpmlourenco/server:<personal-version>
```

Example:

```text
ghcr.io/rpmlourenco/server:2.10.1.dev2
```

The build also verifies the expected base-image structure and compiles the
modified Python files. If any of these validations fail, the image is not
published.

## Relationship with the Home Assistant add-on

The personal add-on catalog is maintained in a separate repository:

```text
rpmlourenco/home-assistant-addon
```

The `music_assistant_personal/config.yaml` file contains both the image name and
the version that Supervisor must install:

```yaml
version: 2.10.1.dev2
image: ghcr.io/rpmlourenco/server
```

The catalog version must match an image tag that has already been published to
GHCR. Update the catalog only after the GitHub Actions image build has completed
successfully.

## Updating from a new stable version

Never blindly copy old Sonos files over a new release. Integrate the new
official code first and review any upstream changes to the same files.

### 1. Prepare the branch

Confirm that the repository is clean and fetch the new commits and tags:

```powershell
git status --short --branch
git fetch upstream --tags
git checkout sonos-https-artwork
```

If the previous version was `2.10.1` and the new tag is `2.10.2`, replay the
personal commits on top of the new tag:

```powershell
git rebase --onto 2.10.2 2.10.1 sonos-https-artwork
```

Resolve any conflicts in the Sonos files carefully. Preserve new upstream fixes
and reapply only the HTTPS artwork option while resolving conflicts.

### 2. Update the base image

Change `UPSTREAM_VERSION` in both locations:

```text
Dockerfile.personal
.github/workflows/publish-personal-image.yml
```

For the example above, the value becomes:

```text
2.10.2
```

### 3. Review and test the patch

Review the complete difference from the new official version:

```powershell
git diff 2.10.2...HEAD -- music_assistant/providers/sonos music_assistant/translations/en.json
git diff --check
```

Run the focused tests:

```powershell
pytest tests/providers/sonos/test_provider.py tests/providers/sonos/test_player.py
```

Also run the repository-wide checks required by the project:

```powershell
pre-commit run --all-files
```

### 4. Choose the personal version

Use the official version as the base and append an incrementing personal
suffix:

```text
2.10.2.dev1
2.10.2.dev2
```

Increment the suffix whenever another image based on the same official version
must be published.

### 5. Publish the branch and build the image

After reviewing and testing the changes:

```powershell
git add <changed-files>
git commit -m "Update Sonos HTTPS artwork build to Music Assistant 2.10.2"
git push origin sonos-https-artwork
```

Start the versioned workflow:

```powershell
gh workflow run publish-personal-image.yml `
  --repo rpmlourenco/server `
  --ref sonos-https-artwork `
  -f version=2.10.2.dev1
```

Wait for the run and confirm that **Build and publish ARM64 image** completes
successfully before proceeding.

### 6. Publish the new add-on version

In the `home-assistant-addon` repository, change only the version in:

```text
music_assistant_personal/config.yaml
```

Example:

```yaml
version: 2.10.2.dev1
```

Validate and publish it:

```powershell
git diff --check
git add music_assistant_personal/config.yaml
git commit -m "Update personal Music Assistant to 2.10.2.dev1"
git push origin main
```

### 7. Update Home Assistant

1. Open **Settings → Apps**.
2. Refresh the repository information.
3. Open **Music Assistant (rpmlourenco)**.
4. Confirm that the new version is offered.
5. Create an appropriate backup.
6. Run the add-on update.

A full Home Assistant restart is not required. Supervisor restarts the add-on
container during the update.

## Post-update validation

Verify the following in order:

1. The add-on reports the expected personal version and returns to **Running**.
2. The Music Assistant interface opens normally.
3. Music providers and players are connected.
4. Albums and artists display images.
5. A new track plays on a Sonos player.
6. Artwork appears in the Sonos application.
7. The Sonos provider still has **Artwork HTTPS base URL** configured with the
   `/ma-sonos-artwork` endpoint and no trailing slash.

If an artist was previously processed without an image, use **Refresh item** in
that artist's menu to force a new metadata lookup.

## Maintenance rules

- Keep the HTTPS artwork work as one focused behavioral change.
- Do not alter unrelated Sonos provider IDs, interfaces, or behavior.
- Always review upstream changes to the same files before updating.
- Do not publish a catalog version before its matching image exists.
- Retain earlier GHCR tags for diagnostics and recovery.
- Do not automatically update or restart Home Assistant during the image build
  process.
- Keep the GHCR image and add-on catalog repository accessible to Home Assistant
  Supervisor.
